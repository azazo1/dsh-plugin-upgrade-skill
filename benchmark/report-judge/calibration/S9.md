# One coordinate mismatch, two symptoms

host-input-contract.ts defines InputState.draft and Occurrence.offset/length in clipboard-text coordinates, where a chip expands to its full clipboardText. EditorProjection.detectText uses one U+FFFC per chip. host-input-facade.ts passes insertReference spans and consumeToken span guards to the detect-text splice. Ordinary text, including a separating space, still counts normally in both projections.

plugin-client.js add uses snapshot.draft.length as its insertion point. On the first paste into an empty composer both lengths are zero, so the insert succeeds. Once a chip exists, clipboard width is greater than detect width. The unconverted insertion point overshoots the host span; insertReference returns false and add emits the changed-composer toast. console-session.txt captures this first-success/second-failure signature. The toast is not evidence of an actual concurrent edit. The chip is one detect character; the entire draft can also contain ordinary spaces, so it need not have detect length one.

The same error affects remove in plugin-client.js: it passes occurrence.offset through offset+length to consumeToken without conversion. The host declines the invalid span. The plugin ignores that result and deletes records[ref] anyway. The occurrence still drives the composer and dock chip, but the missing record makes the dock display unavailable. This is not an independent failed upload.

For a clipboard boundary p, compute detect(p) = p - sum(o.length - 1) over occurrences before that boundary. For insert at draft end, include all preceding chips. For removal, convert the selected occurrence.offset using earlier chips, then remove [detectStart, detectStart + 1). Preserve the draftRev guard and use a current snapshot; do not bypass CAS. Equivalent boundary mapping is fine. Retire the record only if consumeToken returned true; if it returns false, retain bookkeeping and surface/reconcile the failure. A supported setDraft fallback slices the clipboard projection and can retire the record only after that fallback succeeds.

Regression plan: paste A then B in the same session and assert both calls succeed, two composer occurrences exist, and both dock chips render. Remove B with A preceding it and assert exactly B's occurrence, dock chip and record disappear while A remains. A declined consumption must retain B's record and chips. Also check first/last-chip removal and paste after removing all chips. These are proposed assertions, not claimed executed tests. The optional source-reading checklist in task item 5 does not add scoring requirements.
