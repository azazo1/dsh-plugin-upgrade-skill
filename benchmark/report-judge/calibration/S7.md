# Reproducible type-baseline plan

package.json declares @deepseek-ai/dsh-llm as ^0.1.2-alpha.1. README.md and the task's supplied registry inventory say alpha.1 was never published while alpha.2 was. These are the evidence for this report; I did not make an online query. Before later implementation, verify the individual package's versions rather than assuming a root-package dist-tag proves the whole cohort exists.

The caret denotes a range, not an exact alpha.1 pin. The supplied alpha.2 release satisfies it, so installation can succeed by selecting alpha.2. The missing lower-bound release does not force an install failure. The resulting types are alpha.2 types, and successful resolution does not establish the intended alpha.1 baseline or prerelease API compatibility.

My chosen plan is to deliberately target the published 0.1.2-alpha.2 baseline. Change this dev dependency to the exact 0.1.2-alpha.2 version, inspect the plugin's actual SDK imports and align the needed type dependencies to that intended target. This is a conscious target change, not proof that alpha.1 was tested. One complete published-version plan is sufficient; I am not proposing an additional source-build route.

During implementation, keep the project's existing package manager, generate and commit its lockfile, and then use its frozen-install mode (for an npm project, npm ci). Run the project's typecheck, such as tsc --noEmit, against the selected cohort, with runtime checks planned separately where applicable. This report ran none of those commands. Future version changes should be deliberate pin/lock updates with repeated verification. This plan introduces no temporary overrides that would need removing. If alpha.1 is mandatory, it requires a separately verified exact source build and local package resolution, not an npm install of the missing exact release.
