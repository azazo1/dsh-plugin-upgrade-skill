# Release routing diagnosis

ls-remote-tags.txt lists v0.9.7 but not v0.9.5. sync-script.sh loops over origin/public/mirror2 and pushes HEAD:main only; it never distributes release tags. Attempt 1 therefore cannot resolve the documented v0.9.5 on that mirror. There is no supplied evidence for blaming a consumer typo or network failure.

dsh-version.txt gives the consumer's runtime as 0.1.1-rc.2. compat-table.md says plugin v0.9.7 targets the 0.1.2-alpha.1 client API. The useConversation crash in the brief is the new artifact asking the older runtime for a seat it does not provide. Installation success only proves artifact resolution; restarting cannot add the missing API contract.

The runtime is frozen. compat-table.md verifies v0.9.3 against rc.1 and explicitly describes rc.2 as an additive image-preprocessing change, so v0.9.3 is the compatible choice here. However, ls-remote-tags.txt also lacks v0.9.3. First the maintainer must publish that verified release tag to the public mirror, for example git push public v0.9.3. Only after verifying it resolves should the consumer run:

```sh
dsh plugin --profile web add '@org/dsh-ui-progress@github:public-org/dsh-ui-progress#v0.9.3'
```

If tag distribution is delayed, a verified v0.9.3 commit can be an alternative only if that commit is actually reachable from the chosen mirror. Its SHA is not supplied here, so I cannot invent an immediately usable SHA command. Upgrading the frozen runtime or reinstalling v0.9.7 is not a remedy.

Repair sync-script.sh so every mirror receives the intended release tags as well as branch updates, using explicit tag pushes or non-forced git push <remote> --tags. Check each documented tag with a remote listing after release; branch synchronization alone does not satisfy this.

Route README commands by the consumer's dsh --version: 0.1.1-rc.2 maps to v0.9.3; the verified 0.1.2-alpha.1 target maps to v0.9.7. A visible compatibility matrix and separate pinned commands prevent another newest-tag default from breaking older consumers. Later alpha releases require their own verification. These are proposed repairs; no installation or publication was performed.
