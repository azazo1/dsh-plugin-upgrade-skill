# Naming judgment

I read package.json and dsh-plugin.naming.json without changing either. The manifest declares the plugin name greet, coordinate acme/greet and package dsh-greet; these are different naming surfaces. The fixture README explicitly allows the official short name greet. It is not a compatibility error and a publisher prefix is a collision recommendation, not a mandatory rename.

The service search is unprefixed and may collide with another provider, so it merits a warning and later registry review. That does not prove an incompatible service API. A strict policy can reject warnings without changing their underlying classification.

The event web-search/ready is a shared channel. Multiple publishers are not inherently an error: their schemas and existing registry context must be compared. Its present verdict is informational / needs registry context, not an unsupported name conflict.

The other manifest surfaces are loaderIds acme-greet, tools acme_greet_hi, commands acme-greet-hi, skills greet, skillProviders acme-greet-filesystem, settingsNamespaces acme-greet and the exact route /api/plugins/acme-greet/hi. Their local shapes do not establish any global reservation. The scoped names reduce collision risk; the bare skill name deserves registry context as well. No supplied fact establishes a compatibility error for these surfaces, but occupancy and schema/route overlap remain unknown.

I made no online registry query. Every global availability/reservation claim is not checked. Later publication review should compare the declared names, event schemas and route with the registry. It would be wrong to say everything passes or that greet/search are globally available. private:true marks test material and is not a naming incompatibility.
