# S10 — paste renaming and version-chip follow-ups

## 1. Paste-only renaming design

Normalize clipboard items at the paste acquisition boundary, before they enter the
shared `add()` validation.  Equivalently, `add()` can accept an explicit
`acquisition: 'paste'` option and normalize before calling `validateItems()`; it must
not infer paste from a filename or MIME type alone.  This ordering matters because
two clipboard items can both arrive as `image.png`, and the current duplicate check
would reject them before a later rename could run.

For a paste item, use this basename and extension algorithm:

```text
image MIME (or a known image extension when MIME is empty): paste_image
anything else:                                      paste_file
extension: safe final extension from the original item.path basename
            otherwise a MIME-to-extension mapping from item.file.type
            otherwise "bin"
```

Use a lower-case extension.  For example, the normal clipboard `image.png` items
become `paste_image.png`, `paste_image(2).png`, and so on.  A clipboard PDF named
`document.pdf` becomes `paste_file.pdf`; a file with no useful suffix but MIME
`application/pdf` also becomes `paste_file.pdf`.  The original suffix wins over
MIME (so a named `.jpeg` remains `.jpeg`); the MIME mapping is the fallback (for
example `image/jpeg` → `jpg`, `image/png` → `png`, `text/plain` → `txt`).  An
unmapped or missing type uses `bin`, so every generated name has a deterministic
extension.

Allocate the first free name in this order:

```text
paste_image.<ext>
paste_image(2).<ext>
paste_image(3).<ext> ...
```

`paste_file` uses the same suffixing rule.  Probe the unsuffixed name first, then
the smallest available integer starting at 2; do not use the total attachment
count, and do not assume that suffixes have no holes.  Add each allocated name to
the local `taken` set immediately, so a single paste batch is unique even before
the composer publishes its next snapshot.  For separate paste events, take a new
snapshot when the event is handled (and serialize or otherwise reserve concurrent
paste insertions so two simultaneous events cannot allocate the same name).

The authoritative initial `taken` set is the current DSH composer state:
`input.state.getSnapshot().occurrences`, using each occurrence's actual attachment
name/path (the excerpt exposes this as the occurrence label).  That is the live
state against which a new attachment will conflict.  The module-level `records`
Map is bookkeeping and may be used for rendering, but must not decide whether a
name is occupied.  Its subscription deletes a record whenever a snapshot appears
to have no occurrence, including a momentary empty snapshot; using that cache alone
can therefore miss a still-live attachment.  Conversely, a stale record should
not keep a name reserved after the composer no longer contains it.

The paste preprocessor should clone each item with the generated `path`, preserving
the original `File` bytes, and pass those cloned items to `validateItems()` and
`add()`.  The drop path and the file/folder-picker path must pass through unchanged:
their real `item.path` values, including image names, must not be renamed.

## 2. Extension, dock, and upload representation

The generated path is the one user-facing attachment name.  Set both the record's
`label` and the cloned item's `path` to it.  Therefore the dock chip shows
`paste_image(2).png` (or the corresponding `paste_file...` name), and the upload
body's `files[].path` contains exactly that same name.  The underlying browser
`File.name` need not be mutated; the path metadata sent by the plugin is what must
be consistent.

## 3. Follow-up B: cause and display rule

The running bundle knew `PLUGIN_VERSION = '0.2.10'`.  Around 90 seconds after the
`v0.2.11` push, the tag endpoint returned a cached page containing only `v0.2.9`,
`v0.2.8`, and `v0.2.7`; its response showed `x-cache: HIT`, `age: 178`, and a
five-minute shared-cache lifetime.  `latestFromTags()` therefore selected `v0.2.9`
as the maximum of the stale response.  Since `v0.2.9 <= 0.2.10`, the code took the
current-version branch, but `renderCurrentChip(tag)` interpolated the fetched
`tag`, producing “already the latest version v0.2.9”.  The later change was cache
expiry/refresh, not an actual downgrade of the installed bundle.

Compare the normalized remote stable tag with the locally known running
`PLUGIN_VERSION`:

```text
remote > local  -> update chip, showing remote
remote <= local -> current chip, showing local PLUGIN_VERSION
no remote       -> offline/unavailable chip
```

In particular, the current renderer should receive no untrusted tag, or should be
called as `renderCurrentChip(PLUGIN_VERSION)`.  The green message must say
`...latest version 0.2.10` for this example, never the older fetched `0.2.9`.
The remote value is useful for detecting an update, but it is not ground truth for
the version already running.

## 4. Regression tests

Add tests at the acquisition/add boundary, not just tests of a name helper:

1. A paste batch containing three image items whose raw paths are all
   `image.png` succeeds and produces `paste_image.png`,
   `paste_image(2).png`, and `paste_image(3).png`.  A second paste event sees the
   live first-batch occurrences and continues at the next free name.
2. A batch of non-images produces `paste_file.pdf`,
   `paste_file(2).pdf`, etc.; test original-extension precedence and MIME fallback
   (for example no suffix plus `application/pdf`), including the deterministic
   unknown-type fallback.
3. A dragged image and a picker-selected image retain their real names.  This
   proves the behavior is scoped to the paste acquisition path rather than to
   `add()` for every source.
4. Seed the composer snapshot with a live `paste_image.png` occurrence while the
   `records` Map is empty (or after simulating the transient-empty-snapshot
   subscription cleanup); a new paste must choose `(2)`.  Also seed a stale record
   with no live occurrence and verify that the base name is reusable.  These tests
   make the state snapshot, rather than the fragile records cache, the conflict
   authority.
5. Mock `latestFromTags()` to return stale `v0.2.9` while the local constant is
   `0.2.10`; assert the current chip says `0.2.10`, not `0.2.9`.  Also cover equal
   versions and a newer `v0.2.11`, which must select the update chip and show
   `v0.2.11`.

## 5. Lib-only release hygiene

- Bump the package version and hand-update every inlined running-version constant,
  especially `PLUGIN_VERSION` in the shipped `lib` bundle.  Verify the bundle and
  package metadata agree with the release tag; do not reuse an old tag or leave the
  bundle identifying the prior release.
- Run the regression suite and a syntax check against the actual distributed file,
  such as `node --check lib/client.js`, plus the normal diff/packaging checks.  With
  no build step, the edited lib file is the artifact; there is no generated bundle
  that will repair a missed hand edit.
- Publish/replace that updated lib artifact through the plugin's normal distribution
  or installation channel, then have users update/reinstall and reload it.  A Git
  tag and a hard refresh do not deliver a new lib bundle, and this plugin has no
  host-side update endpoint.  The tag fetch only advertises an update; it cannot
  apply one.  Release validation should also tolerate a temporarily stale tag API
  response and must never use that response to rewrite the locally known running
  version.
