# S15 — Vanishing Dock Chips: the Silent Slot Crash

## Root cause

The primary fault is the `busy` reference in the shipped `AttachmentChips`
component:

```js
disabled: (props.input?.phase ?? 'plain') !== 'plain' || busy
```

`busy` is a state variable local to `AttachButton`; it is not declared in
`AttachmentChips`, nor passed in through `props`. Therefore, when JavaScript
evaluates the right-hand side, it throws `ReferenceError: busy is not defined`.
The two functions are sibling functions, so the local binding in
`AttachButton` is not visible to the chip component.

This is data- and state-path dependent:

1. `AttachmentChips` returns `null` when there are no matching occurrences.
   In that empty state, the `map` callback is never entered and the button
   props object containing the faulty expression is never evaluated.
2. When an occurrence exists, the callback builds the chip and evaluates
   `disabled`.
3. The `||` makes the defect intermittent/latent. If the input phase is not
   `plain`, the left side is `true` and JavaScript short-circuits without
   resolving `busy`. If the phase is `plain`, the left side is `false`, so
   JavaScript evaluates `busy` and throws.

Thus the guard did not make the reference safe; it only hid it on the
non-plain path. A v0.2.10 user could pass through the empty state or a
non-plain render without seeing the problem. The decisive state for a
regression test is a matching occurrence with `phase: 'plain'`.

The exception occurs while the dock slot entry is rendering, before the
element tree is returned. The framework's slot-level error boundary catches
the exception and unmounts the whole `InputZone` entry (`AttachmentDock`),
not merely the remove button whose props were being constructed. The attach
button is a separate slot and has its own valid `busy` binding, so it remains
visible. The only diagnostic is the boundary/React error in the browser
console; there is no user-facing error banner. This explains why paste and
send can still work while the dock appears to have vanished.

## Bisection and the v0.2.11 timing trap

The timestamp is not proof that the hover-preview code introduced this
failure. The v0.2.10 source and the maintainer's thread both show the same
`|| busy` expression before the hover change. The correct isolation is:

- Run a minimal render of the v0.2.10 `AttachmentDock` with one occurrence
  whose `source` is `SOURCE` and with `input.phase === 'plain'`, under the
  slot error boundary. It reproduces the exception at `busy`.
- Alternatively, roll back only the hover additions and render the dock. If
  the same line still fails, re-add the hover changes one at a time only after
  fixing the baseline. An empty-state mount is not a valid bisect because it
  returns before the faulty line.
- A genuinely new hover regression would have a passing baseline mount and
  would fail only after a particular hover change is reintroduced, with a
  stack location in that newly added code. An old latent bug fails on the
  baseline mount at the pre-existing line; the new release merely changes
  timing/data so the previously untested, data-present path is exercised.

There is also a separate source-review issue visible in the supplied diff:
the added `imageItem` declaration appears before the `occurrences.map`
callback, while `status` and `record` are declared inside that callback. If
the excerpt reflects the literal shipped source, that is an independent new
scope error (and can mask the older `busy` failure). `imageItem` must be
computed inside the per-occurrence callback. That observation does not make
the pre-existing `busy` reference safe; both paths need to be isolated and
tested rather than attributing every failure to the hover feature.

## Fix and hardening

Remove the dangling `|| busy` from `AttachmentChips`, leaving the phase guard
there, unless the component is deliberately given a busy value. If the chip
really must reflect attach-button busy state, pass that state explicitly as a
prop (or expose it on the input model); do not rely on a sibling component's
local variable.

Inside the per-occurrence callback, the hover lookup should also be defensive,
for example:

```js
const imageItem = status !== 'missing'
  ? (record?.items ?? []).find(item => isImagePath(item.path))
  : undefined;
```

`record?.items.find(...)` protects the missing `record` case but still throws
when a record exists without an `items` array. The `?? []` fallback is cheap
insurance in a slot component, where incomplete or transitional data should
not remove the entire slot.

The click guard should likewise tolerate a non-Element event target:

```js
if (event.target?.closest?.('.remove')) return;
```

(Equivalently, normalize the result and test it for truthiness.) Calling
`event.target.closest(...)` unconditionally can throw when `target` has no
`closest` method, producing the same slot-level failure. Optional chaining is
an inexpensive boundary around host/browser data.

## Regression test

Add a render smoke that exercises the non-empty path, for example in the
project's existing component test harness:

```js
it('renders a dock chip for a pending occurrence without a slot error', () => {
  const capture = vi.fn();
  render(
    <SlotErrorBoundary onError={capture}>
      <AttachmentDock
        input={{
          phase: 'plain',
          occurrences: [{
            source: SOURCE,
            ref: 'r1',
            label: 'screenshot.png',
            occurrenceId: 'o1',
          }],
        }}
        remove={vi.fn()}
      />
    </SlotErrorBoundary>
  );

  expect(screen.getByRole('button', { name: /Remove screenshot\.png/ }))
    .toBeInTheDocument();
  expect(capture).not.toHaveBeenCalled();
});
```

The fixture for `records` should contain the matching record when the test
uses the hover path. The important assertions are that the chip element
exists and that the slot boundary did not capture an error. A test with
`occurrences: []` alone is insufficient because that is the early `return
null` path and never reaches the faulty expression.

## Release-process lesson

`node --check` validates parsing only. An unresolved identifier such as
`busy` is valid JavaScript syntax, so syntax checking cannot detect it; it
also does not execute the component with data in the slot. A lib-only plugin
can therefore pass `node --check` while failing as soon as the host renders a
real occurrence.

The minimum viable pre-ship check for a slot-rendering library is to load the
built artifact in the same component/test environment used by the host and
mount every registered slot at least once with representative data. For this
plugin that includes a non-empty pending-attachment dock in the ordinary
`plain` phase, with an error-boundary capture (and preferably `console.error`)
assertion, plus the attach-button smoke. Keep the empty-state case as a
separate check, but do not treat it as coverage of the data-present render
path.
