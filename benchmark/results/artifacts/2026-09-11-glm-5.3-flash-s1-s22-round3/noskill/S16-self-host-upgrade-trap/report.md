# S16 · The Self-Host Upgrade Trap — Diagnostic Report

## 1. Structural root cause: why the in-session global upgrade fails by construction

The evidence pack fixes the topology in `agent-session-log.txt`: the agent session is
"running INSIDE a dsh web session, GUI at http://127.0.0.1:3080, host process =
node .../node_modules/@deepseek-ai/dsh/...". The session and its tool worker are not
external clients of dsh — they are child processes/threads inside the very package npm
was asked to replace. The upgrade target and the executor of the upgrade are the same
artifact, so the failure is structural, not accidental:

- The tool call `npm install -g @deepseek-ai/dsh@0.1.2-rc.1` ran "inside the host's own
  worker process". npm's first phases are `npm warn cleaning node_modules/@deepseek-ai/dsh`
  and `npm info remove @deepseek-ai/dsh` (16:41:02–16:41:05) — it deleted the running
  host's own code directory out from under it while the host was executing from it.
- What dies first is the host process, and with it the web GUI: the log shows
  "at this point the web GUI session DIED (browser tab: connection lost)" at ~16:41:31,
  during `npm info linkStuff`. The host dies first because any lazily required module,
  spawned subprocess, or restart-sensitive path now points at a directory being rewritten.
- Why the tool call never returned: the log records `[tool result] <no result recorded —
  the tool call was interrupted after it was recorded, but no result was durably recorded.
  Its outcome is unknown.>`. The result would have had to travel session → host → web GUI,
  but the host — the sole relay for that result — is the casualty of the install. No host,
  no result channel, regardless of whether npm itself eventually finished.

So "upgrade dsh from a dsh session" is self-contradictory by construction: the actor, the
victim, and the reporter of the outcome are the same process.

## 2. The broken state afterwards

From `env-state.txt` (AFTER) and the post-mortem shell transcript in `agent-session-log.txt`:

- The package content survived: `node_modules\@deepseek-ai\dsh\  <present, partially
  replaced>` with rc.1 files. But `env-state.txt` marks it "NOT a standard install" —
  files were placed "by hand during a partial manual repair attempt by the user". npm
  never completed its `linkStuff`/bin-linking phase for the global prefix.
- The shims died: the session log shows `dsh.ps1   <stale, points into the old tree>` and
  `dsh.cmd   <MISSING>` (and `dsh` likewise missing). Shims are generated by npm at the end
  of a global install; the install was interrupted mid-`linkStuff`, so they were never
  regenerated, and the stale `dsh.ps1` points into a tree that no longer exists. Hence
  `dsh --version` → "The term 'dsh' is not recognized…" even though the package directory
  is full of valid rc.1 files: the command depends on the shim, not the directory.
- Why hand-swapping makes it worse: `repair-notes.md` states the directory "had been
  replaced/manually swapped, and the dsh / dsh.cmd shims were never generated — so the dsh
  command was actually dead". A hand-copied tree (a) lacks the registry-recorded install
  metadata npm uses for future upgrades/removals, (b) still has no valid shims — copying
  files does not regenerate the `dsh` / `dsh.cmd` / `dsh.ps1` bin links — and (c) leaves
  version-mismatched leftovers (the `dsh-old-0.1.1-rc.1` backup plus the stale `dsh.ps1`)
  that a later real install must untangle. The `env-state.txt` verdict is explicit: "the
  dsh CLI itself is unusable; only an external tool (another agent CLI) can repair the
  install."

## 3. The repair that was actually applied

From `repair-notes.md`:

1. Re-run the formal registry install from outside dsh:
   `npm install -g @deepseek-ai/dsh@0.1.2-rc.1`.
   This is the only repair that works where the in-session attempt could not, because the
   installer now runs from an external shell/CLI whose own executable lives in a different
   package — deleting and relinking `node_modules/@deepseek-ai/dsh` cannot kill it, and
   npm's full lifecycle (including bin-linking) runs to completion: "dsh / dsh.cmd /
   dsh.ps1 all regenerated; dsh --version -> 0.1.2-rc.1". A formal install also replaces,
   rather than patches around, the non-standard hand-swapped directory.
2. Aligned the source checkout from the alpha.5 tag to the `dsh-v0.1.2-rc.1` tag; "no
   local-modification conflicts" — so host-source references match the installed version.

Verification: `dsh --version` → `0.1.2-rc.1` after shim regeneration, plus the user-side
steps the notes leave open — "start dsh --profile web, hard-refresh the browser, confirm
plugins load (whale / progress / etc.)" — the real-machine check that the host and GUI
actually come back healthy.

## 4. The protocol the agent should have followed

Recognition: the agent's own process, the session, the tool worker, and the web GUI all
live inside `node_modules/@deepseek-ai/dsh` — the exact directory the requested upgrade
rewrites. That makes this a self-upgrade, and the agent must not execute the global
install itself, even though it has a working shell tool. "Do it for the user" stops at the
boundary where success destroys the executor and even a completed run can never report its
result. The correct deliverable is an external procedure handed to the user (order matters):

1. Before npm runs: exit/shut down the running dsh host and web GUI first — nothing that
   depends on dsh may be executing while npm deletes and relinks the global tree. Keep a
   repair path ready in case the install is interrupted: an external agent CLI or plain
   shell, never dsh itself.
2. Run from an external shell (not from any dsh session) the exact formal install:
   `npm install -g @deepseek-ai/dsh@0.1.2-rc.1` — the registry install, not a directory
   swap or file copy, because only a formal install regenerates the `dsh`, `dsh.cmd`, and
   `dsh.ps1` shims and leaves standard install metadata.
3. Afterwards: verify `dsh --version` → `0.1.2-rc.1`, start `dsh --profile web`,
   hard-refresh the browser, confirm plugins load; then optionally clean the `dsh-old-*`
   backups.

Which parts are known rules vs. new: the version-diff findings (below — 252 files, all
version bumps, zero API/feature changes; plugins migrated for 0.1.2-alpha.x need no
re-migration) follow from the existing upgrade rules that already govern version bumps and
plugin migration. New for this incident is the self-host boundary rule itself: an agent
running inside the dsh host must never execute a global dsh install/upgrade from within a
session; it must hand the user an external procedure with the shut-down-first ordering.
That discipline rule did not previously exist and is the lesson of S16.

## 5. Prevention

Agent-side guard. Before running any package-manager install/upgrade command, the agent
(or a shell-tool wrapper) should check whether the target package is an ancestor of its
own executable — resolve the running host path (`node_modules/@deepseek-ai/dsh/...`, per
the session-log context header) against the install target `@deepseek-ai/dsh`. On match,
refuse the tool call with an explanation and emit the external procedure of §4 (shut host
down → external shell install → verify) instead of executing. The guard key is
"executor ∈ upgrade target ⇒ never execute"; it also covers any sibling tool whose binary
lives in the same global tree.

Post-upgrade checklist for this machine (informed by the alpha.5→rc.1 findings):

1. `dsh --version` reports `0.1.2-rc.1` and `dsh` / `dsh.cmd` / `dsh.ps1` all exist and are
   fresh (regenerated by the formal install, not stale pointers into the old tree).
2. Start `dsh --profile web`; hard-refresh the browser; GUI reconnects at
   http://127.0.0.1:3080 and plugins load (whale / progress / etc.) — the notes leave this
   real-machine verification to the user.
3. Source checkout tag aligned to `dsh-v0.1.2-rc.1` with no local-modification conflicts.
4. Given the diff finding — "252 files, ALL of them package.json version bumps. Zero
   API/feature changes" — confirm no re-migration is owed: plugins migrated for
   0.1.2-alpha.x need no re-migration for rc.1; verify plugins still load (step 2 covers
   this) rather than redoing migrations.
5. Only after rc.1 is confirmed working, clean up the `dsh-old-*` backup directories (e.g.
   `dsh-old-0.1.1-rc.1`) and any hand-copied leftovers from the user's partial manual
   repair, so future installs start from a standard tree.
