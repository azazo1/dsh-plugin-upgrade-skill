# S21 Diagnostic Report — The Resource Service That "Unavailable"

Deployment: dsh 0.1.5-alpha.1 → 0.1.5-alpha.2 in-place npm-global upgrade on Windows 11, profile created under 0.1.2/0.1.3, six external client plugins junction-linked. Evidence: symptom-log.txt, boot-manifest-excerpt.txt, combo-probe.txt, contrast-probe.txt, console-excerpt.txt, discussion-excerpt.txt.

## 1. Attribution — which layer actually fails

**The failure is not in static artifact serving and not in the filesystem: it is in the runtime resource-provider chain that the sidebar tab's read depends on — specifically the api-workspace-files Remote read, whose metadata never arrives at the tab.**

- **Layer ruled out — module serving.** combo-probe.txt Probe 3: all 62 manifest entries return HTTP 200, zero 404s. The documentpreview tab module itself loads, since the tab opens, renders the correct title ("sidebar-open-test-2.md"), and shows a styled placeholder rather than a load error.
- **Layer ruled out — the file and its accessibility.** contrast-probe.txt: two readers of the same file (E:\deepseek-harness\test-lhh010\.dsh\tmp\sidebar-open-test-2.md, session-scoped address dsh-resource://file/session/session-2844c12c-5870-41e0-bb46-7d1fdc7c183a/.dsh/tmp/sidebar-open-test-2.md):
  - file-trace plugin (own host RPC, /dsh-file-trace/* routes): READS FINE — 原文 and 阅读 modes both show the content.
  - documentpreview sidebar tab (api-workspace-files Remote): FAILS.
  Two readers succeeding-vs-failing on the same file at the same moment rules out file permissions, file absence, workspace-root resolution, and the OS layer. It isolates the difference to the *transport each reader uses*: file-trace's own RPC works; the tab's api-workspace-files resource read never completes.
- **Where the read stalls, per the metadata status.** contrast-probe.txt: "meta.status stays 'none', the tab shows 文件资源服务不可用。" A metadata status stuck at 'none' means the tab issued its request and the resource metadata response never arrived at all — the request stalled or was dropped between the client tab and the resource provider, rather than returning an error payload (which would set a failed status and an error message). The tab's fallback string 文件资源服务不可用。 is the UI's rendering of "no metadata ever came back", not a diagnostic from the resource system itself.
- Consistent with this, console-excerpt.txt and symptom-log.txt item 4 show **no red errors from documentpreview or the sidebar** — the tab did not crash or reject; it silently never received the resource metadata.
- Host-side context from contrast-probe.txt: the workspace-files host row IS present in the web-app bundle patch (cordis.patch.yml), outside-workspace files are allowed by the read() contract ("files outside it are allowed" — index.ts read() doc), and workspace-root resolution goes through a typert lookups.register entry (sessions.get(sessionId)?.header.cwd, fallback sandboxPolicy.workspaceRoot). So the stall point is the provider-side resource chain on this upgraded profile — the same "resource-provider chain did not take over" behavior documented for alpha.1 in discussion-excerpt.txt — not any of the layers above.
- The earlier, distinct dialog ("no registered tab type claims dsh-resource://file/absolute/E:/deepseek-harness/dsh-input-history/package.json") is a **separate, already-explained** failure: per boot-manifest-excerpt.txt, alpha.2 replaced ui-sidebar-textpreview (which registered the "text" tab type claiming dsh-resource://file/**) with ui-sidebar-documentpreview, whose tab's canOpen accepts only parseFileAddress(address)?.scope === 'session'. Absolute-scope links are now unclaimed by design, not by breakage.

## 2. Probe discipline — which combo probe is valid

- **Valid: Probe 3, the per-module sweep** — 62/62 HTTP 200. Each URL is exactly the form the boot manifest issues for each module (Probe 1 confirms a single-module manifest URL, /plugins/??@deepseek-ai/dsh-api-gateway/client.js&rev=234716e8f7370214-0, serves 200 with 73,616 bytes). This faithfully measures static artifact serving: every listed module's client.js is available at the current rev.
- **Invalid: Probe 2, the all-62-modules-joined URL** — 404 with zero-length body on a ~4–5 KB URL. It does not measure artifact availability; it measures the combo route's request-URL length/parsing limits. The real loader never issues such a URL, so the 404 only shows that oversized synthetic joins are rejected. **It must never be cited as "modules missing"**: it contradicts the 62/62 sweep on the same host and rev, and citing it would send the investigation toward a nonexistent mass-module outage. (In the alpha.1 round in discussion-excerpt.txt there WAS a real roster/combo mismatch at the same rev — new roster rows 404 while old rows served 200 — which makes this invalid probe tempting; alpha.2's evidence shows that condition is gone.)
- **How the real loader fetches the roster:** the host publishes the roster in __DSH_BOOT__ (boot-manifest-excerpt.txt: 60 entries, fetched same-origin after restart), and the loader fetches each module per its individual manifest url entry (single-module combos like /plugins/??@deepseek-ai/dsh-api-workspace-files/client.js&rev=234716e8f7370214-3). The valid serving measurement is therefore "each manifest URL returns 200", which Probe 3 performs and passes.

## 3. Distractor separation

- **The dsh-paste-input "fold skipped (parse failed)" warnings are unrelated to the content-read failure.** Per console-excerpt.txt, they repeat "for every historical paste-attachment message" and concern the ==== DSH_PASTE_INPUT_V1 ==== marker protocol and the .dsh/tmp/attachments/<session>/<send>/ bubble-collapsing logic — a client-side message-rendering/fold feature on old messages. They are warnings (▲), not errors; they come from a different plugin on a different code path (message bubbles, not the sidebar/resource read). File them separately.
- **What else changed in the roster between versions:** per boot-manifest-excerpt.txt, alpha.2 **replaced** packages/client/ui-sidebar-textpreview with packages/client/ui-sidebar-documentpreview (packages/bundle/web-app/cordis.patch.yml now carries the ui-sidebar-documentpreview row; the old row is gone — 0 substring mentions of ui-sidebar-textpreview in the boot HTML). This roster change **does not explain the content-read failure**: it fully explains only the absolute-scope claim error (the new document tab's canOpen accepts scope === 'session' only). The session-scoped tab opens correctly, and its empty content is the stalled resource metadata read of §1 — a provider-chain failure that discussion-excerpt.txt shows already occurred on alpha.1, i.e., not newly introduced by the textpreview→documentpreview rename.

## 4. Mitigation decision — order of action

- **Do not work around it in the plugin.** Rewriting, retrying, or adding a fallback read inside documentpreview would paper over a host-side resource-provider failure, duplicate an existing capability (file-trace already proves a working RPC face), and desynchronize from upstream. The plugin has no bug here: it opens, titles the tab, and faithfully reports "service unavailable" when metadata never arrives.
- **First cheap step (maintainer, minutes): restart the host again and re-probe.** discussion-excerpt.txt records that a host restart self-healed the alpha.1 roster/combo mismatch; an in-place npm-global upgrade on a profile created under 0.1.2/0.1.3 is exactly where a second restart can reconcile the newly-served tree. Verify read-only: re-fetch __DSH_BOOT__, confirm the workspace-files row, retry the session-scoped link, and check whether meta.status leaves 'none'.
- **Escape hatch (verified): rollback.** discussion-excerpt.txt documents rollback to the previous published version (npm i -g @deepseek-ai/dsh@0.1.3-alpha.2) as the working escape hatch on this profile. If restart does not heal, roll back to restore service; preserve the alpha.2 tree/profile state for forensics.
- **What goes upstream:** the §5 forensics package, cross-referenced to discussion #5999 round 2 (comment 18371079) since this is the second round of the same failure family on the same deployment. Separately, the absolute-scope "no registered tab type claims …" gap is worth an upstream feature request (an absolute-scope fallback tab type), not a local workaround.

## 5. Prevention / upstream

**Forensics a complete upstream report needs:**
- Versions and topology: 0.1.5-alpha.1 → 0.1.5-alpha.2 in-place npm-global; Windows 11; profile created under 0.1.2/0.1.3; six junction-linked external client plugins; dsh web restart output ("[dsh-profiles] ready", no terminal errors).
- Exact failing addresses and both outcomes: the absolute-scope dsh-resource://file/absolute/E:/deepseek-harness/dsh-input-history/package.json claim error (dialog 无法打开文件/重试), and the session-scoped dsh-resource://file/session/session-2844c12c-5870-41e0-bb46-7d1fdc7c183a/.dsh/tmp/sidebar-open-test-2.md tab that titles correctly but shows 文件资源服务不可用。
- The contrast probe result: file-trace's own RPC reads the same file fine (原文/阅读 both show content); the sidebar tab's api-workspace-files read never arrives; **meta.status stays 'none'** — the single most diagnostic datum, locating the stall in the resource-provider chain.
- The probe-discipline evidence: 62/62 per-module HTTP 200 at rev=234716e8f7370214, plus the explicit caveat that the 62-joined 404 is a URL-length artifact, not missing modules.
- The roster diff: ui-sidebar-textpreview → ui-sidebar-documentpreview replacement in packages/bundle/web-app/cordis.patch.yml; presence of the dsh-api-workspace-files host row; its inject rows (@deepseek-ai/dsh-api-gateway, @deepseek-ai/dsh-client-resources) from __DSH_BOOT__.
- Prior art: link to discussion #5999 (alpha.1 round: roster/combo mismatch self-healed by restart, resource-provider chain still failed, rollback verified), marking this report as round 2.
- Console excerpt proving no sidebar/documentpreview errors (with the dsh-paste-input warnings flagged as unrelated distractors).

**Boot-time loud-failure checks the host could add** so this class renders an error instead of an empty tab:
- After client activation, verify that every tab type required by the roster/patch actually registered, and that each client module's declared inject entries (dsh-api-workspace-files injecting @deepseek-ai/dsh-client-resources) resolved to a live provider — fail loud at boot, and make "loaded without registering" name the missing provider, not just the first unregistered entry as in #5999.
- A boot self-probe of the resource chain: perform one synthetic dsh-resource://file/session/… metadata read through the workspace-files Remote and surface a non-zero result as a boot warning, instead of discovering the stall per-tab at click time.
- Health-check consistency between the roster and the combo route at the same rev (the #5999 mismatch class): a boot-time HEAD/GET of each manifest URL, failing loudly rather than serving a roster that points at unserved artifacts.
- Client-side: when a tab's resource metadata does not arrive within a timeout, render a retry affordance with a diagnostic id and log a console error — the current 文件资源服务不可用。 placeholder, meta.status 'none', and zero console errors hide the stall from both user and maintainer.
