# Plugin migration procedure

This is a document-only adaptation of the supplied migration procedure. Follow the
task's authorization, output location and evidence limits. The task already grants
any approvals stated in it; do not wait for another reply. No packaged helper,
worked-example directory or external lookup is required by this procedure.

## 1. Establish scope and a baseline

Identify whether the task is inspection, installed-plugin update, or source
migration. Keep inspection read-only. Record the current source, installation
identity, plugin version, host corridor and applicable file ownership from the
fixture and supplied facts. Preserve unrelated changes and unknown configuration.
For an executable task, run the available baseline checks before edits and record
existing failures. For a static fixture, describe the checks without claiming to
have executed unavailable commands.

## 2. Connect the corridor before changing code

Use the supplied reference index's from/to metadata to connect the complete
corridor, then compute the target's net state. Do not order versions by filenames.
Record an unsupported segment or unavailable API coordinate as unconfirmed; use
only the target source and declarations already supplied by the task. Do not
invent an API to bridge a missing edge.

## 3. Map the actual touchpoints

Use the supplied pre-flight checklist to inspect source patches, events,
services/Remote, host filesystem, UI/commands/tools, custom channels, and
subprocess/output. Record files and expressions, including no-hit categories and
scan limits. Filter the supplied cards by the actual Host/Web Client/plugin face
and target corridor. A scan with no matches still needs dependency/import review
and the checks that the fixture can support.

## 4. Plan and execute within the task's scope

Group the required changes by seam. Link each change to its source evidence,
target behavior and verification. Use one package-management track, preserve
unknown fields, and keep rollback limited to the paths changed by this task.
Optional capability changes are suggestions, not mandatory migration edits.
Where source modification is authorized, land the change in the task-designated
fixture; otherwise provide the diagnosis and plan without changing it.

## 5. Verify the applicable layers

Check dependency resolution, profile enablement, static checks, runtime
activation, one core behavior path, and wrapper exit/output/cancellation/teardown
where the task supplies the required runtime. Separate a successful install or
build from evidence of actual runtime behavior. Check available source facts for
exact contracts rather than assuming a passing check proves every layer.
Use ordinary installed tools and the fixture's supported commands; do not invoke
or fetch any missing helper. If a layer cannot run, report the limit explicitly.

## 6. Report evidence and limits

Separate pre-existing failures, completed changes/checks, skipped items, uncertain
facts or residual risks, rollback boundaries, and optional recommendations.
Distinguish proposed checks from observed results. Preserve diagnostic details;
do not automatically retry an unknown failure without an applicable retry policy.
When local observations conflict with supplied sources, record both rather than
silently choosing one. Stop unsupported changes, while completing the report.
