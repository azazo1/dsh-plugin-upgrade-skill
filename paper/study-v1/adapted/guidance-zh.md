# 插件迁移流程

这是原迁移流程的纯文档适配版。遵守题目授权、交付位置和证据边界；题目已明确
授权的动作不再等待确认。本流程不要求执行未供应的 helper、读取示例目录或联网。

## 1. 明确范围并记录基线

区分只读检查、已安装插件升级和源码迁移。检查任务保持只读。根据 fixture 和资料
记录代码来源、安装身份、插件版本、宿主走廊与文件所有权，保留无关修改和未知字段。
可执行任务先运行现有基线检查并记录既有失败；静态夹具只说明验证方案，不声称运行
了缺失的脚本或工具链。

## 2. 先连接走廊，再计算净状态

按引用索引的 from/to 元数据连接完整走廊，不按文件名排序。计算目标最终净状态后
再提出修改。缺少走廊边、目标源码或 API 坐标时明确标为待确认；仅使用题目已供应的
目标源码与声明，不凭记忆虚构接口来填补缺口。

## 3. 根据实际触点筛选资料

按 pre-flight 清单扫描源码 patch、事件、服务/Remote、宿主文件系统、UI/命令/工具、
自建通道和子进程/输出，记录文件、表达式、未命中类别及扫描限制。结合实际
Host/Web Client/普通 plugin 面与目标走廊筛选卡片。零命中仍需检查依赖和导入，
并完成当前夹具允许的验证。

## 4. 按授权实施最小变更

按迁移接缝分组，说明来源证据、目标行为与检查方法。使用一种包管理轨道，保留未知
配置，回滚仅覆盖本次拥有的路径。可选 capability 只作为建议。题目授权改源码时，
把变更落在指定 fixture；只读题仅提交诊断和计划。

## 5. 分层核对

依次核对适用的依赖解析、profile 启用、静态检查、运行时激活、核心行为及包装器的
退出码、输出、取消和清理。安装或构建成功不能替代运行行为证据。用供应的资料核对
精确契约，用已安装普通工具和夹具支持的命令检查；不执行或获取缺失 helper。
缺少运行条件的层级如实注明未验证。

## 6. 报告证据与限制

区分既有失败、已完成、跳过、待确认/残留风险、回滚范围和可选建议；区分验证计划
与实际观察。保留诊断信息，不在没有适用重试策略时自动重试未知失败。
本地观察与来源冲突时并列记录；停止无依据修改，同时完成报告。
