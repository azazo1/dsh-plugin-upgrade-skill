\begin{abstract}
Skills package procedural guidance and reference material for language-model agents, but a gain from supplying a skill does not by itself establish a benefit from its procedural organization.
We study this distinction in plugin migration across breaking releases of \framework{}, with a planned controlled evaluation of the current 56-task inventory spanning static diagnosis and hands-on repair. The existing \BenchmarkTaskCount{}-task snapshot is retained as historical documentation; the new inventory awaits quality control and freezing.
The benchmark combines version-specific upgrade knowledge, executable Host contracts, and repository contexts containing misleading comments, pre-existing failures, or stale artifacts.
Because tasks and skills share source material, we distinguish open-book utility from generalization to incidents excluded from skill development.
We propose a controlled comparison of no injected material, generic migration guidance, source-matched reference documents, and distilled skills, together with paired clean/trap variants and an audited knowledge holdout.
The current evidence comprises heterogeneous calibration and development runs; it does not yet establish the incremental value of procedural organization or independent incident transfer.
We provide the benchmark infrastructure and an evaluation design that separates functional correctness, diagnostic quality, and citation compliance, making these questions testable without assuming that skills help.
\end{abstract}

\section{Introduction}

Migrating a plugin across framework releases requires more than replacing API names.
An agent must identify the relevant version contract, distinguish migration failures from unrelated defects, and verify that the repaired plugin behaves correctly in its target environment.
Version-sensitive code generation and migration remain active evaluation problems \citep{versicode,codemenv}.
A practical source of guidance is an agent \emph{skill}: a package of instructions, reference documents, and sometimes executable helpers supplied at inference time.
Existing benchmarks measure skill utility through paired evaluation and report that effects depend on the task and configuration \citep{skillsbench,swe-skills-bench}.

A positive with-skill difference, however, admits several explanations.
The package may supply missing API facts, organize those facts into an effective procedure, provide useful scripts, or simply induce more computation.
These effects matter operationally, but they support different scientific claims.
A generic-advice baseline does not isolate procedural organization from specific information, and a benchmark used repeatedly to refine the skill cannot also serve as an independent test of that refinement.
These distinctions motivate our evaluation design.

We study plugin migration in \framework{}, an open-source agent framework.
The historical snapshot described here contains \BenchmarkTaskCount{} tasks, with version-locked fixtures and automatic graders that combine diagnosis, contract checks, and, where applicable, Host execution.
Some tasks present contradictory local evidence: obsolete comments recommend an incorrect change, an unrelated test already fails, or a stale artifact obscures the migration defect.
This setting lets us examine not just access to migration knowledge, but how agents use it when repository evidence conflicts with instructions.
We do not assume that the target APIs are absent from model training data or that successful startup establishes complete functional correctness.

We organize the study around three research questions:
\begin{itemize}
\item \textbf{RQ1: Incremental utility.} Does a distilled skill improve migration correctness over both no injected guidance and source-matched reference documents?
\item \textbf{RQ2: Incident transfer.} Does a frozen skill help on incident families excluded from its development, and how does this differ from retrospective knowledge holdout?
\item \textbf{RQ3: Context conflict.} Does a skill reduce the performance penalty caused by misleading context, and when does following it instead produce an error?
\end{itemize}

The repository already contains benchmark infrastructure, historical model runs, a knowledge-holdout audit, and a semantic-grading pilot.
The controlled experiments needed to answer all three questions remain incomplete.
Accordingly, this revision separates existing evidence from the proposed protocol rather than presenting anticipated gains as findings.

\section{Related Work}

\paragraph{Evaluating agent skills.}
SkillsBench evaluates curated skills with paired conditions and deterministic verifiers \citep{skillsbench}.
SWE-Skills-Bench uses execution-based acceptance tests for software-engineering tasks and reports heterogeneous utility, including degradation under version-mismatched guidance \citep{swe-skills-bench}.
Thus, neither paired evaluation, executable grading, nor negative skill effects is unique to our study.
Our focus is their application to community-informed migration incidents, with controls for information content, development exposure, and misleading repository context.

\paragraph{Version-aware code migration.}
VersiCode studies version-specific completion and version-aware migration \citep{versicode}; CODEMENV evaluates compatibility, definition changes, and adaptation across environments \citep{codemenv}.
Our proposed comparison varies the form of externally supplied migration knowledge while holding the task and agent configuration fixed.
We do not characterize prior migration benchmarks as measuring only memorized knowledge.

\paragraph{Conflicting contextual instructions.}
Indirect prompt injection demonstrates how instructions embedded in retrieved data can redirect an LLM-integrated application \citep{indirect-prompt-injection}.
Our tasks examine an engineering reliability setting: obsolete comments and artifacts can conflict with the intended version contract without constituting a deliberate security attack.
Whether skills mitigate such conflicts requires a clean/trap intervention, not merely a positive average on tasks containing traps.


\section{Setting and Skill Corpus}

\subsection{Scenario}
\label{sec:scenario}

\framework{} is an open-source, plugin-based agent framework with a plugin marketplace and a fast release cadence.
Each minor release carries breaking changes: renamed exports, auth-plane restructurings, build-artifact layout drift, session-state projection changes, and version-routing rules.
Plugin authors---often not the framework authors---must migrate their plugins across these releases, and the failures they hit are recurring, concrete, and loudly discussed in the community issue tracker.
Two properties make this setting attractive for measuring skill utility.
First, version-specific contracts make it possible to identify which facts the supplied materials contain and which can be inferred from the fixture; neither observation establishes what a model has memorized.
Second, the framework ships a host CLI that can cold-boot a plugin in an isolated profile, giving us a host-side liveness oracle for execution-level grading (\S\ref{sec:grading}).

\subsection{Upgrade cards}
\label{sec:cards}

The unit of field knowledge in our setting is the \emph{upgrade card}: a short, structured document contributed by practitioners after a migration incident.
A card records five fields: \emph{symptom} (the observable failure), \emph{root cause} (the framework change responsible), \emph{fix} (the minimal required change to the plugin), \emph{affected versions} (source and target), and \emph{provenance} (a link to the community incident: issue, discussion, or pull request).
The intended admission procedure requires reproduction of the symptom against the recorded version pair. A complete per-card provenance and reproduction audit remains required before claiming that every task is independently grounded in a verified incident.
Cards organize the knowledge from which both the skill corpus and benchmark tasks are derived; their claims must be checked against the target implementation (\S\ref{sec:construction}); Table~\ref{tab:card} shows one card from the corpus.

\subsection{Skill corpus}
\label{sec:corpus}

The repository contains skills for upgrade auditing, migration, release, testing, orchestration, and authoring, together with additional supporting skills. Each experiment must pin the actual supplied package rather than infer its contents from the maintained tree.
We focus on the flagship \emph{plugin-upgrade} skill: it covers the framework's breaking-change patterns and the evidence-first procedure for diagnosing them (symptom $\rightarrow$ observed behavior $\rightarrow$ minimal fix).
The maintained tree also contains supporting field examples, so an evaluation cannot assume that the current checkout is answer-free.
Temporal tasks use the corpus frozen before their cards, and any task with a later answer-bearing example declares a pre-example \texttt{skill\_snapshot\_commit}; the evaluation protocol mounts that snapshot rather than the current tree.
Such pinning excludes known later examples; semantic overlap and feedback from task development require separate audits.

\subsection{Adversarial design}
\label{sec:adversarial}

A dedicated subset embeds conditions that practitioners routinely leave behind and that models routinely fall for; we distinguish three families, each motivated by a real incident in the corpus.
(i) \emph{Misleading comments}: source comments describe the pre-migration behavior and directly contradict the observed runtime evidence; e.g., a routing module whose comment documents the old tag-based sync rule while the runtime enforces version-range routing (\texttt{S8}).
(ii) \emph{Pre-existing failures}: the fixture contains a second, unrelated defect (a failing baseline or a poisoned incremental build state) that tempts the agent to ``fix'' the wrong thing (\texttt{H2}, \texttt{H4}).
(iii) \emph{Stale artifacts}: incremental build state can obscure the source of a failure (\texttt{H4}); this family can overlap with pre-existing failures. The localization trap \texttt{H7} instead concerns fragile display-text anchoring and must not be mislabeled as a stale artifact.
These task descriptions motivate candidate strata; final family assignments and clean/trap equivalence checks remain to be audited before the analysis in \S\ref{sec:misleading}.

\subsection{Grading}
\label{sec:grading}

Historical hands-on graders combine Host execution with static contracts, diagnosis, and task-specific compliance checks.
Host signals include cold boot, registration, dispatch, and version-locked contract invocation; they test particular behaviors rather than complete plugin correctness.
Some static graders use card identifiers or lexical patterns, which can favor the condition that receives those identifiers.
The S1--S4 semantic-judge pilot instead assesses evidence and migration claims, but it has not yet established independent human agreement.

The planned primary endpoints separate functional correctness from diagnostic quality and citation compliance.
Both arms must be scored by the same frozen grader and rubric; historical and revised scores are not interchangeable.

\subsection{Quality control}
\label{sec:qc}

Oracle admission and execution-contract validators provide initial checks of task solvability.
They do not establish that a grader rejects plausible wrong answers or accepts alternative correct repairs.
The formal admission audit therefore includes unchanged fixtures, defective but bootable repairs, alternative valid solutions, and semantic-grading stress tests.
Evaluator failures must remain distinct from candidate failures, and the evaluated agent must be isolated from grader internals and reference answers.
Package metadata such as \texttt{private: true} is not a filesystem access control.


\section{Experimental Setup}
\label{sec:setup}

\paragraph{Protocol status.}
The design below is proposed for a fresh evaluation of all 56 current tasks (17 S-, 14 M-, and 25 H-prefixed tasks), subject to quality control and a new frozen manifest. The generated \BenchmarkTaskCount{}-task inventory and appendix currently document the historical snapshot and will be moved to historical documentation when the new main table is generated. Historical scores will not populate the new main result table. It must be frozen before collecting its test outcomes and does not retroactively describe the heterogeneous historical runs.

\subsection{Paired protocol}
\label{sec:protocol}

Comparisons are paired within task, model, scaffold, fixture, grader, tool surface, and resource budget.
Conditions run in fresh isolated environments in a balanced, interleaved order.
The experiment manifest will distinguish solver access to external documents from provider traffic, installation traffic, and verifier access.
The authorization convention \texttt{BENCHMARK-AUTH-v1} does not by itself prove network or filesystem isolation.
Native skill catalogs and memory must be disabled and audited for a literal no-skill condition; otherwise the condition is labeled no-injected-skill.

The primary study allocates one complete agent run to each task--configuration--condition cell: 56 tasks, two configurations, and four conditions yield 448 runs. The primary statistic is the task-average paired reward difference using the first run in each cell. Before formal outcomes are observed, a stratified subset of $K$ tasks will be fixed using task mode, incident family, and trap type; each of its cells receives two additional runs, costing $16K$ extra runs. Subset three-run means and variability are reported separately as stability analyses, without replacing first-run scores in the main table.
Confidence intervals will resample incident families while preserving condition pairing and within-family task weights. These intervals describe between-family sampling uncertainty and do not fully measure within-task generation variability under the single-run design.
We will report functional pass rates, per-task deltas, negative effects, coverage, and resource usage.
Evaluator errors follow a predefined retry and missing-data policy; a valid candidate that fails within its budget remains an observed task outcome.

\subsection{Models and agent scaffold}
\label{sec:models}

The initial design targets two complete model--scaffold configurations under all four conditions, with one run per cell in the main evaluation.
Model, provider, scaffold version, reasoning settings, prompts, and tool permissions will be recorded for each configuration.
Differences across configurations are descriptive system comparisons; skill effects are estimated only within matched configurations.
Historical model names do not guarantee identical serving implementations.
% TODO T14: register exact configurations before formal runs.

\subsection{Conditions}
\label{sec:conditions}

We propose four conditions: A, no injected guidance; B, generic migration guidance; C, source-matched raw cards or reference documents; and D, distilled skill.
C and D must cover the same permitted facts and use comparable retrieval access, context budgets, and tools.
Any executable helpers supplied only with D are part of the package intervention and require a separate ablation for a document-only claim.
D--A measures package utility; D--C addresses procedural organization subject to the remaining content and budget differences.
D--B alone cannot distinguish specific knowledge from its organization.

\subsection{Source overlap and development exposure}
\label{sec:teaching-to-test}

Tasks and skills share upgrade knowledge, making open-book utility a legitimate but limited endpoint.
A separate development-exposure ledger must identify tasks whose rewards, trajectories, solutions, or graders informed skill refinement.
Related incident families are grouped before assigning independent test membership; a different task identifier does not ensure independence. Rerunning all 56 tasks does not erase prior development exposure: the full-pool result measures utility on that fixed pool. Independent incident transfer and clean/trap mechanism studies are separately budgeted extensions; until completed, their corresponding claims remain open questions.

The existing temporal-holdout audit identifies knowledge absent from a frozen skill tree.
This differs from a prospective incident split: a newly written card can describe an older incident, and its task may already have informed later skill development.
Known answer-bearing examples are excluded by task-specific skill pinning, but path absence alone is not a semantic leakage test.
The task-specific boundary for \texttt{H11} is distinct from the global holdout freeze; it must not be silently substituted for that freeze.

\section{Planned Analysis}
\label{sec:analysis}

\subsection{Temporal holdout}
\label{sec:holdout}

The existing v1 audit classifies 10 tasks as clean knowledge holdout, 17 as mixed, and 25 as ineligible in its own 52-task candidate inventory.
These counts describe that audit, not the \BenchmarkTaskCount{}-task historical snapshot or a finalized independent test.
We will cross-check candidate membership against development exposure and distinguish retrospective knowledge holdout from prospective incident transfer.
The primary comparison uses absolute within-task differences and confidence intervals.
A ratio to in-distribution gain is only supplementary, since it is unstable when that gain is near zero and the two sets may differ in difficulty.

\subsection{Where gains or losses occur}
\label{sec:where-gains}

We will examine effects by annotated information coverage, fixture inferability, task mode, and incident family.
Unaided performance is an observed baseline, not proof of training-data membership.
Annotations will be fixed without consulting test outcomes, and subgroup analyses will be labeled confirmatory or exploratory before testing.
No monotonic relationship between coverage and skill gain is assumed.
% TODO T5: replace with annotation agreement and family-aware conditional analysis.

\subsection{Misleading context}
\label{sec:misleading}

Each selected task will have clean and trap variants with the same repair objective and grader.
Let $d_t^{\mathrm{trap}}$ and $d_t^{\mathrm{clean}}$ denote D--A reward differences for the two variants of task $t$.
The interaction $I_t=d_t^{\mathrm{trap}}-d_t^{\mathrm{clean}}$ tests whether skill provision changes the penalty from misleading context.
We will report the four cell means, a family-aware interval for the interaction, and trace evidence of how the conflict was resolved.
A positive skill difference on trap tasks alone is insufficient to identify this interaction.

\subsection{Failure taxonomy and over-trust}
\label{sec:failures}

Candidate labels include misapplication, procedure drift, ordinary task failure, and over-trust, with unknown and multiple labels allowed.
Over-trust requires evidence that the agent accessed a rule, encountered contradictory evidence, continued to follow the rule, and produced an incorrect action.
A negative reward difference alone does not establish that sequence.
Two annotators will classify traces independently, recording agreement and denominators separately for all skill-arm failures and paired regressions.
Evaluator failures are reported outside this behavioral taxonomy.

\subsection{Transfer tasks}
\label{sec:transfer}

The maintained benchmark includes real-project and contract-level tasks such as \texttt{H9}, \texttt{H11}, and \texttt{H22}.
They remain within the same framework ecosystem and do not establish cross-ecosystem portability.
Each task must have an explicit inventory and exposure status before contributing to a transfer estimate; tasks outside the historical snapshot require a separate manifest.

\section{Discussion}
\label{sec:discussion}

\paragraph{A living benchmark.}
The benchmark is designed to grow with the framework: each new breaking release produces new community incidents, new verified cards, and new distilled tasks, under the same provenance and oracle-admission invariants.
The repository provides task-contribution guidance. Future releases should preserve provenance and development-exposure records so that growth does not silently change an evaluation set.

\paragraph{Transferability.}
\framework{} is the first instance of the methodology, not its boundary.
Other frameworks may support a similar construction when versioned contracts and reproducible incidents are available. The effort and validity of that extension remain to be measured.

\paragraph{Hypotheses for skill authors.}
Evidence-first guidance may help an agent resolve conflicting repository instructions, but this is a hypothesis rather than a validated design principle in the current evidence.
A matched ablation should remove that procedural guidance while preserving migration facts and resource budgets.
Likewise, checklist refinement must be evaluated on tasks excluded from the feedback used to construct it.

\section*{Limitations}

This is an incomplete empirical draft.
The frozen \BenchmarkTaskCount{}-task inventory covers one framework family and contains related tasks, so its size overstates the number of independent incidents unless family structure is accounted for.
The main four-condition comparison, independent grader validation, and prospective incident evaluation remain pending.
Historical runs use heterogeneous protocols and sometimes expose native skills or external resources; some raw records are unavailable for re-audit.
The target framework and skill materials are public, so absence from model training data cannot be guaranteed.
Knowledge absence from a frozen skill is not equivalent to absence from model priors or from researcher development feedback.
Finally, cold boot and narrow contract checks establish only the behaviors they exercise; citation compliance and reference-answer agreement are not substitutes for functional correctness.

\section*{Ethics}

The release audit must document source licenses, attribution, and consent where required for incident excerpts and fixtures.
A complete per-item audit is pending; public availability alone is not treated as permission to redistribute every artifact.
Formal runs should use disposable environments with declared resource and access boundaries.
Before publishing trajectories, the release process must remove credentials and personal data while preserving auditable task, configuration, and scoring evidence.
